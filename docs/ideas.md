# Ideas (not planned)

Measured or studied options that were deliberately left out. Each one lists what would justify revisiting it.

## 1. Polyphase float kernel instead of libsamplerate at ratio ≈ 1

**Status:** rejected for v1 (2026-10). Revisit only if users report a battery / energy problem.

### Measurement

During a call, about 90 % of Jumphertz's CPU time is libsamplerate's `sinc_mono_vari_process` (medium
quality) on the output IO thread. Profiled with `ps -M` (per-thread CPU time) and `sample` (1 ms) on the
release binary running both legs:

| Thread | Share of the thread's time |
|---|---|
| Output IO (BlackHole): libsamplerate | ≈ 1.8 % |
| Output IO: rest (ring, PI loop, latency, L+R copy, HAL loop) | ≈ 0.1 % |
| Input IO (Scarlett) | ≈ 0.05 % |
| Main thread (1 Hz tick, status every 5 s, AppKit run loop) | ≈ 0 |

The same call pattern (512-frame blocks, input dosed per block, ratio nudged every block) costs:

| libsamplerate | Performance core | Efficiency core |
|---|---|---|
| Medium, 48 → 48 kHz | 0.39 % | 1.59 % |
| Medium, 44.1 → 48 kHz | 0.37 % | 1.77 % |
| Fastest, 48 → 48 kHz | 0.18 % | 0.80 % |

macOS places the lightly loaded real-time IO thread on efficiency cores, about 4× slower for this code but
far more power efficient; Activity Monitor reports time, whatever the core. Compiler flags (`-O3`,
`-mcpu=apple-m1`, FMA contraction) changed nothing measurable.

### The option

For ratio ≥ 1, libsamplerate's `calc_output_single` interpolates every coefficient between two points of its
table with one fraction for the left wing and the complementary fraction for the right wing. That is exactly
a linear blend between two rows of a polyphase matrix with 491 phases (the table's native resolution). Rows
generated by running libsamplerate's own formula on an impulse give the same filter; two `vDSP_dotpr` of 94
float taps per output frame replace the double-precision loop.

Prototype (scratch benchmark, efficiency core): 0.19 % instead of 1.6 % (≈ 8×). Expected agent total during
a call: 0.3–0.4 % in Activity Monitor.

Differences from libsamplerate: float instead of double accumulation, and no filter stretch when the ratio
drifts a few ppm below 1 (stretch of 1e-5): expected deviation around −120 dB.

### Planned safeguards (if ever implemented)

- Used only for ratio ≥ 0.995; libsamplerate stays for everything else (> 50 kHz inputs).
- No change to the ring margin, target, PI loop or the discard-on-underrun rules. The filter-centre position
  becomes exact by construction (no need to mirror libsamplerate's ratio ramp).
- New equivalence test: same input and ratio sequence through libsamplerate and the kernel, difference
  < −110 dB at 44.1 → 48 kHz and at 48 → 48 kHz ± 200 ppm.
- The whole DSP suite unchanged must pass (30 simulated minutes, quality, underrun, overflow, rate change).
- A config switch, off by default until a 30-minute hardware session with the usual criteria validates it.

### Why not now

It puts a second, home-made DSP path in the real-time code, which is what choosing libsamplerate avoided.
The real cost is ≈ 0.4 % of a performance core during calls and 0 % otherwise: the gain is mostly cosmetic.

## 2. Run the legs only while Discord actually captures from BlackHole

**Status:** to study after the first round of user feedback.

Today both legs run whenever Discord is running, including when it sits open outside any call. On macOS 14+,
the HAL exposes process objects (`kAudioHardwarePropertyProcessObjectList`, `kAudioProcessPropertyBundleID`,
`kAudioProcessPropertyIsRunningInput`, `kAudioProcessPropertyDevices`): Jumphertz could start the legs only
while a Discord process is running input on BlackHole 2ch, and stop them (with a grace delay) afterwards.

The objection raised in phase 0 (another capture app such as MiniMeters keeping BlackHole busy) no longer
applies: BlackHole 2ch is reserved for Jumphertz.

To check before implementing:

- Which Discord process does the capture (helper vs main app bundle ID) and whether the property is reliable
  across Discord, PTB and Canary.
- Latency of the notification vs the first words of a call (the legs need ~30 ms to converge).
- Fallback for macOS 13 (current behaviour).
- Discord's microphone test and voice activity setup also open the input.

## 3. Latency levers (measured, off by default)

- `outputBufferFrames: 128` on Jumphertz's own IOProc on BlackHole: ≈ −16 ms expected. Hardware session B
  postponed until after the first round of user feedback.
- `reducedLatencyMargin`: ≈ −4 ms. Skipped: not worth any risk.
